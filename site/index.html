What it is

Rationale that survives the handoff.

AI agents help write code, but the reasoning behind it often stays in prompts, chats, and disconnected documents. Axiom defines the domain, policies, and workflows that keep those connections — exercised in this repository through a Codex harness and a Go implementation.

  • 01

    Intent gets lost

    Specifications

    Outcomes, constraints, and acceptance criteria are recorded before code is written.

  • 02

    Context fragments

    Projects

    A Project relates independent repositories without treating any single one as the whole.

  • 03

    Decisions drift

    Plans & ADRs

    Plans and architecture decisions become durable references for humans and agents alike.

  • 04

    Completion lacks proof

    Evidence

    Validation and Evidence make results inspectable and reproducible, not merely asserted.

Spec-Driven Development. The reason for a change stays connected to its implementation and its acceptance evidence.

How it works

One lifecycle, for people and for agents.

Each step produces the context the next step consumes.

  1. 01

    Specify

    Intent becomes a Specification with outcomes, constraints, and acceptance criteria, before any code.

  2. 02

    Plan

    Decisions and the plan are recorded; architecture choices with lasting impact become ADRs.

  3. 03

    Execute

    Implementation runs in bounded Executions on Codex or Claude, and material choices wait for human approval.

  4. 04

    Validate

    Validation and review produce Evidence and reconcile the docs. Acceptance remains a human decision.

Today each step is driven by humans together with the harness and the Runtimes. Dynamic orchestration remains future work.

Getting started

From install to your first workflow.

Using Axiom needs no clone, Go toolchain, or build.

  1. 01

    Install

    The installer verifies the SHA-256 checksum before extracting and installs axiom into $HOME/.local/bin, without sudo.

  2. 02

    Verify

    axiom version reports the installed version and revision.

  3. 03

    First run

    axiom first-run finds Codex and Claude on your PATH and installs Axiom's skills for each. It never installs a Runtime or touches credentials.

  4. 04

    Configure a Project

    Guided: it previews the exact change and writes nothing until you answer yes.

  5. 05

    Run the workflow

    Create a Work Item as a GitHub Issue, then start and inspect its bounded workflow.

Installer

Install from the terminal.

The commands from the Getting Started guide, from install to your first workflow.

# install the latest stable release

$ curl -fsSL https://raw.githubusercontent.com/rgomids/axiom/main/scripts/install.sh | sh
$ axiom version
$ axiom first-run

# relate repositories to one Project

$ axiom project configure
$ axiom project show --selector my-project

# run the bounded workflow for Issue #123

$ axiom workflow start --project my-project --repository main --number 123
$ axiom workflow status --project my-project --repository main --number 123

Supported hosts: Mac and Linux. Full Getting Started guide.

Project status

What exists today — and what does not.

Delivered capabilities and planned capabilities are listed separately, on purpose.

Available

  • The axiom CLI, installable from versioned releases with no clone or Go toolchain
  • Codex-first harness: context, policies, skills, templates, and deterministic validation
  • Tested Go implementation of Project rules, portable and machine-local state, Runtime installation, GitHub Work Items, and a bounded persistent Lingo workflow
  • Codex and Claude Runtime integrations, configured by axiom first-run
  • Canonical completion and provenance contracts, with fail-closed local publication and recovery
  • MVP delivery slices S1 – S7 delivered on main, with versioned Specifications, ADRs, and Evidence

In progress

  • S8 — multi-runtime planning and multi-agent execution: technically complete, awaiting human review

Future work

  • Runtimes and adapters beyond Codex and Claude
  • Work Item providers beyond GitHub Issues
  • Dynamic or distributed orchestration
  • Runtime token and cost budget governance
  • Portable distribution and synchronization across machines

Nothing under Future work is implemented, and nothing there is authorized to be implemented. Technical validation or a merge does not imply human acceptance. This summary follows the versioned project status, which remains the source of truth.
